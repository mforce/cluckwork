# Slices: Entity-scoped audit history

Build order. Each slice ends in a working, testable state.

1. **Tracer bullet — minimal wiring.** URL becomes the source of truth for both `action` and `entityId` (`useSearchParams`; both move together — `usePagedList`'s fetcher depends on both, they can't be half-migrated without breaking the reload trigger), the `isLikelyGuid` guard (needed from the start — without it, the first hand-edited bad URL 400s), a naive heading (`rows[0]?.entityType`, no `reloading` gate yet — accepted as temporarily wrong during a reload, fixed in Slice 2), entity column still shown (not yet hidden), generic empty message still shown (not yet distinguished), one `<Link>` on `FlocksPage`. No backend change — the endpoint/filter already exist. **Proof is a manual browser check** (click "Audit history" on a Flock, confirm the scoped view), not an automated end-to-end test — stated plainly per the Gate 4 template's own sanctioned proof methods, rather than implied as stronger coverage than it is.
2. **Harden the scoped view.** The `reloading` gate on `scopedEntityType` (fixes the stale-heading case accepted in Slice 1), entity-column hiding, the distinct `scopedEmptyMessage`. Grouped into one slice because all three touch the same rendering path and the same test-file section; considered splitting into three micro-slices (per review feedback) and rejected it as disproportionate fragmentation for changes this tightly coupled.
3. **Remaining "Audit history" links.** Flocks (Slice 1) is the pattern; Grades, Sales Orders, Expenses, and Daily Entries (`HistoryPage`) are mechanical repetitions of it — one smoke test each, intentionally not re-proving the pattern. **`StockPage` (Egg Lots) is called out separately**, not lumped into "mechanical repetition": it already has a movement-ledger "History" toggle on the same row, so the new link needs a visibly distinct label and a test that the two do different things (link navigates, toggle expands in place) — the one page in this slice with genuine variation.
4. **The Flow A′ test — a gap this review round found, not previously planned.** Gate 3's test plan covers a fresh navigation into `/audit?entityId=A` and an action-filter change while scoped, but never tests clicking a *different* record's link while already on `/audit` (`entityId` changing from A to B without a remount) — the primary record-to-record browsing flow, and the highest-risk untested path in the whole design. Add it: mount scoped to A, simulate navigating to B's link, assert the fetch re-fires with B's `entityId` and the heading updates to B's type rather than staying on A's.
5. **Backend metric** — the `Program.cs` `EnrichDiagnosticContext` line and its four `RequestLoggingTests.cs` cases. Already correctly ordered after the frontend slices (an earlier review pass argued for moving it later on the grounds that a metric observing a not-yet-built affordance is meaningless — checked against this doc's own numbering: it was already last-but-one, after both frontend slices, not before them. The word "independent" in the original draft meant *testable without the frontend*, not *sequenced before it* — clarified here since it read as the latter).
6. **Docs sync** — `GLOSSARY.md` extension, `HelpPage.tsx` bullet (its own `help` i18n namespace, per Gate 3's Files list). Last, since the content depends on the feature's finished shape.

**Correction to the original plan**: es/tl translations are **not** their own trailing slice. This project's standing i18n policy is translate-now — every batch ships es/tl inline with the English key, not deferred (see the `common.recordHistory`, `audit`, and `help` keys new in this feature: each lands in es.ts/tl.ts in the same slice that introduces it in en.ts). The original draft's "i18n parity" slice conflated that mechanical inline work with the docs-sync step above, which is legitimately a distinct last step because *its* content — not its translation — depends on the finished feature.

**Left open, not resolved here**: who actually consumes the `EntityScopedAuditRequest` metric (dashboard, alert, periodic manual query) is unstated in every gate doc so far. The test suite can only prove the property is *set*, not that anyone *reads* it — worth a one-line answer from the product owner before or shortly after Slice 5 ships, so the metric isn't infrastructure nobody looks at.

**Checked and not changed**: a reviewer question about whether `rows[0]` could ever mix entities across rows in a scoped response — no, the repository's `entityId` filter is an exact-match `WHERE EntityId = @id`, established back in Gate 2; a scoped response is homogeneous by construction. And the concern that `StockPage`'s "visually distinct" requirement can't be verified by Vitest (true — it's a design property, not a DOM assertion) — accepted as a real limitation of unit-test coverage rather than routed to a new Playwright spec; adding browser-driven E2E coverage for one label's visual distinctness is disproportionate to this ticket's stated SPA-only, Vitest-level scope.

Each slice's own test list is otherwise already fully specified in `03-program-design.md`'s Test plan.
