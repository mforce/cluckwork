Proposed state

Same process, same single database. What changes: the API calls a contract, DI wires it to exactly one hidden implementation, and peer implementations can no longer see each other.

FIG 03 · §2.3

Cross-module writes that stay synchronous

Seams that must not become eventually-consistent, because Cluckwork needs atomic ledger updates, FIFO lock ordering, and today's HTTP/idempotency contract preserved exactly. The audit-row node appears only where the current handler already injects IAuditWriter — codex review, PR #423 round 6: SubmitDailyEntryHandler and ConfirmSaleHandler inject none today, so this plan's no-behavior-change rule means their panels must not show one either.

FIG 05 · plan §0–10

Delivery roadmap

Ten phases, each gated on the one before it finishing green. Solid arrows are stated dependencies; the dashed arrow into Phase 9 reflects that Insights only needs the ownership manifest from Phase 1, not the write-side moves.

Top five risks named in the design (§11)
  1. Breaking an atomic ledger/cache transaction while replacing repository calls with seams.
  2. Changing FIFO lock acquisition order and introducing deadlocks or allocation races.
  3. Leaking EF/entity types through a convenient contract, recreating coupling under new names.
  4. Weakening tenant or credential fail-closed behavior through duplicated contexts/adapters.
  5. Allowing compatibility adapters to become permanent, leaving two callable architectures.
