# Credential epoch revocation (#364)

> **Rule** — the one-paragraph version lives in [`AGENTS.md`](../../AGENTS.md); this file is the relocated rationale (what shipped, why the short version was insufficient, what not to break).

**Credential epoch revocation (#364):** every access and refresh token is bound to the user's `CredentialEpoch`; all password-reset paths bump it so already-issued credentials fail on their next use. Epoch **`0` is permanently retired**: users start at `1`, legacy refresh rows start at `0`, and a missing or malformed `credential_epoch` claim is always a mismatch — never default the parsed claim to the current database epoch or otherwise treat it as an exemption. `CredentialEpochMiddleware` deliberately performs a fresh database read for every authenticated request; the round trip is the fail-closed revocation guarantee, so do not cache it. Keep the middleware after `TenantResolutionMiddleware` (the lookup is tenant-scoped) and before `MustChangePasswordMiddleware`; `/api/v1/auth/logout` is deliberately exempt so a superseded credential can still terminate its own session. Login and step-up snapshot the epoch + security stamp that the password actually verified **before** clearing the failed-access count, then refuse issuance if a concurrency-loss reload reveals different credentials — never let an old password adopt a concurrent reset. Their disabled-account branches still pay exactly one real password-hash cost, but must not mutate failed-access/lockout state; `AccountLockout` applies the same boundary after a concurrency reload, stopping rather than charging a stale failure to a newly disabled or reset credential. The SPA serializes refresh and self-password-change through the same per-tab queue + cross-tab Web Lock because both replace the shared HttpOnly cookie — a late old-epoch refresh must never overwrite the fresh pair that keeps the self-changing device signed in. This epoch is distinct from #283's first-login password-change flag, #265's operator-only break-glass temporary password, and #308's single-use browser step-up grant: the mechanisms have different audiences and lifetimes and none substitutes for another.

## Where the read lives (#857)

Since #857 the read is `ICredentialEpochVerifier.VerifyAsync`, implemented by `CredentialEpochVerifier` in `Infrastructure.Identity` and registered Scoped. It runs the same single query, with the same precedence: unknown user, then disabled user, then suspended farm, then epoch. It keeps no state and lets a failed read throw. `CredentialEpochMiddleware` keeps the claim parsing, the logout and `/error` exemptions, and the 401 responses, and its position in `Program.cs` is unchanged. `CredentialEpochFreshReadTests` uses a bearer, changes its row over an independent connection, and expects the next request to be refused. It also counts exactly one credential read on every fault-free request with the host clock's `GetUtcNow` frozen, so a cache that expires on `TimeProvider.GetUtcNow` can only hit; `GetTimestamp` and `CreateTimer` are not frozen. Another test holds one request's read in flight and requires an overlapping request with the same bearer to run its own read. The class runs in a collection that never runs alongside another test class, because any concurrent save of a user or account row would empty a cache that the application clears on its own writes, and hide it. `CredentialVerdict.Current` is not the enum's zero value, so a `default` verdict refuses.

## The stored-epoch floor (#1031)

A missing or malformed claim parses to 0, so "always a mismatch" needs the stored epoch to be at least 1. Before #1031 nothing enforced that, and a stored `0` admitted claimless, malformed and `"0"` bearers, minted tokens at login and rotated a matching refresh row. A CHECK and three refusals now hold it, each independently:

- `CK_AspNetUsers_CredentialEpoch` (`"CredentialEpoch" >= 1`, migration `AddCredentialEpochFloor`) makes such a row unwritable.
- Login refuses a stored epoch below 1 exactly as it refuses a disabled user: one password hash for a correct or incorrect password, an identity-free `LoginFailed`, `Identity.InvalidCredentials`, no lockout change and nothing minted.
- `CredentialEpochVerifier` answers `Superseded`, after the unknown, disabled and suspended checks.
- `RefreshAsync` refuses at the same line that compares `IssuedEpoch`, ahead of grace and replay detection, so a revoked row cannot revoke the user's live sessions.

`CredentialEpochFloorTests` drops the constraint on its own database and proves each refusal, including matching negative epochs that HTTP parsing alone would never reach. `CredentialEpochFloorConstraintTests` proves the constraint and that the migration refuses an existing bad row. `refresh_tokens.IssuedEpoch` keeps its default of 0 and has no CHECK, because a legacy or defaulted row must stay representable and unusable. `StepUpLogoutEpoch` is a different counter, and 0 is a valid value for it.

**Before deploying `AddCredentialEpochFloor`**, run this against the target database:

```sql
SELECT "Id", "AccountId", "CredentialEpoch" FROM "AspNetUsers" WHERE "CredentialEpoch" < 1;
```

Any row stops the deploy. The migration repairs nothing: it fails with `23514: check constraint "CK_AspNetUsers_CredentialEpoch" of relation "AspNetUsers" is violated by some row`, the `migrate` verb exits 1, and the migration is not recorded as applied. Never set a bad row to 1. Bearers and refresh tokens issued at epoch 1 may still be outstanding, and setting the row back to 1 makes them valid again. Choose an epoch above every epoch that user was ever issued, at least one above the highest `IssuedEpoch` among the user's `refresh_tokens` rows, and treat the user's existing sessions as revoked.
