# Generated PostgreSQL schema documentation (#417)

> **Rule** — the one-paragraph version lives in [`AGENTS.md`](../../AGENTS.md); this file is the relocated rationale (what shipped, why each choice, what not to break).

**What shipped.** `docs/schema/` — a GitHub-readable catalog of the deployed PostgreSQL schema (per-table pages with columns/types/nullability/defaults, every constraint with its full `pg_get_constraintdef` text, every index with its full `pg_get_indexdef` text, plus a full mermaid ERD and five subject-area viewpoint diagrams) — generated by [tbls](https://github.com/k1LoW/tbls) from an **ephemeral migrated database**, via `tools/schema-docs/generate.sh`. `tools/schema-docs/generate.sh --check` regenerates into a temp directory and byte-diffs against the committed docs; CI runs it as a step in `build-and-test`.

**Why a live database and not the EF model.** The schema contains artifacts EF reflection cannot see: the four `lower("Name")` expression unique indexes exist only as raw SQL in the frozen `InitialCreate` (see [`407-migration-freeze.md`](407-migration-freeze.md)), partial-index predicates and the `FarmLogos` check constraint render differently once Postgres normalizes them, and a freshly migrated database already contains the 21 base-reference rows (noted in the catalog's description; the rows themselves are documented in [`283-migrations-base-provisioning.md`](283-migrations-base-provisioning.md) — tbls documents structure, not row contents). Introspecting `pg_catalog` on a database the repository's own migrations just built is the only representation that is true by construction.

**Why tbls.** The only surveyed tool that natively emits committed-markdown + mermaid AND captures expression indexes, partial predicates, and check constraints (it reads `pg_get_indexdef`/`pg_get_constraintdef` — verified against its Postgres driver source, not its README). mermerd does only diagrams; SchemaSpy is HTML-native; hand-rolling means owning several hundred lines of introspection + emission + diff code that tbls already is.

**The generator's shape, and why each piece is what it is.**

- **Ephemeral Postgres on a private docker network** — the same digest-pinned image every other stack uses. The `migrate` step runs on the **host** (it needs the published loopback port, Docker-assigned to avoid free-port races); the tbls container reaches Postgres by container name over the network. Two different network paths on purpose — host networking is Linux-only and `host.docker.internal` is Docker-Desktop-only; this shape works on both.
- **`ASPNETCORE_ENVIRONMENT=Testing`** — the same environment the integration-test factory uses, for the same reason: Development would load the developer's user-secrets into the run (breaking clean-checkout parity — the generated output must not depend on whose machine ran it), and Production's serving guards/TLS floor are aimed at a serving process, not a one-off local migrate. The host still boots before CLI dispatch, so the script supplies an ephemeral runtime-generated JWT keypair, mirroring `ci.yml`'s migrate step. A future *registration-time* guard (one that runs before CLI dispatch) can still break the generator — if you add one, run `tools/schema-docs/generate.sh` before pushing, the same way #370 makes you run the sim harness.
- **`tbls doc --rm-dist`, never `--force`** — `--force` overwrites pages but does not delete the page of a dropped/renamed table, leaving a stale file that makes `--check` red forever with no regeneration able to fix it. `--rm-dist` clears the target first.
- **`--user "$(id -u):$(id -g)"`** — the tbls image runs as root; without this the generated files come out root-owned on Linux.
- **`format.sort: false`** — the catalog documents the *real physical column order*; alphabetizing it would misrepresent the database, which is the exact failure #417 exists to prevent. Ordering is stable because the schema comes from frozen, append-only migrations. Determinism was verified by generating twice from independent containers (fresh password, fresh port) and byte-comparing — and CI's `--check` re-proves it cross-machine on every run.
- **`disableOutputSchema: true`** — tbls otherwise also emits a `schema.json` machine dump; markdown is the deliverable.
- **`diff -r` in check mode, not `tbls diff`** — `tbls diff` compares the live database against the docs and cannot notice a committed file tbls no longer generates; the temp-dir byte diff is strictly stronger.

**The guards** (`SchemaDocsTests`, all walk-everything shapes per [`407-writing-a-guard.md`](407-writing-a-guard.md), each mutation-verified):

1. **Postgres-pin uniformity** — every `postgres:<tag>@sha256:` occurrence in every *tracked* file must be one identical string. Before #417 the ~11 copies (test files, `ci.yml`, both compose files) were kept in sync by code comments alone; the docs must be generated against the same Postgres everything else runs. Note the sweep reads `git ls-files` — an **untracked** file is invisible to it (that is how the first mutation run survived), so the guard's guarantee starts at `git add`.
2. **No environment leakage in the committed docs** — no absolute paths, timestamps, or connection URIs. The CI byte-diff would also catch most leakage, but as an unexplained mismatch that tempts re-baselining; this fails **by name**. A *stable* leak (identical on every machine, e.g. the `/work` container mount path) would survive the byte-diff entirely — only this guard catches that class.
3. **Catalog completeness against the live schema** — every table must have its page; every `pg_indexes` row must appear by name **and full definition** (an index quietly changed from expression to plain-column keeps its name — the definition text is what catches it); every PK/unique/FK/check constraint by name and full definition (FK defs carry the `ON DELETE` action). Measured by querying the migrated database, not a hand-kept list, so a future migration's new expression index is in scope automatically.

**Deliberate accepts.**

- The tbls image digest is pinned in a shell script, which Dependabot's `docker` ecosystem does not parse — the pin **rots silently** and is bumped manually. Accepted for a doc generator: immutability (post-2026-03 supply-chain incidents) matters more than freshness, and `--check` diffs catch any output change a bump introduces.
- The CI check runs in `build-and-test`, which has no path filter — web-only PRs pay it too (~30-45s; the postgres image is already warm from Testcontainers, the tbls pull is cold). Chosen over a new path-filtered job because CI cost here is counted in jobs, not seconds. If it grates, the e2e-smoke path-filter pattern is the documented alternative.
- Two concurrently open migration PRs both regenerate `docs/schema/`; the second to merge goes stale and must **rebase and regenerate — never hand-resolve a conflict under `docs/schema/`**.
- The five viewpoint table lists in `.tbls.yml` are hand-kept. A table missing from every viewpoint still appears in the README ERD, its own page, and the completeness guard — viewpoint membership is presentation, not coverage.
- The runner/dev machine needs Docker, `openssl`, and tzdata (the migrate step boots the host, which asserts an IANA canary per #264 — any full glibc distro or the CI runner qualifies).
