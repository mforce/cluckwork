# Help prose naming a control: checked by review, not by a guard (#688)

> **Rule** — the one-paragraph version lives in [`AGENTS.md`](../../AGENTS.md); this file is the relocated rationale (what shipped, why the short version was insufficient, what not to break).

**Status:** accepted
**Date:** 2026-09-05

**Help prose naming a control is checked by READING the catalog, not by a guard (#688).** `catalogParity` compares key SETS, so a translated string that renames a control passes it, `typecheck`, Vitest, CodeQL and review together: in #678 the `es` help text called the expiry field *caducidad* in one string and *vencimiento* in another while its label said `Vencimiento`, and the `tl` text called it *pagkaluma* — becoming obsolete — which is not an expiry date. It was caught by a grep nobody was required to run. The obvious fix, a table of `{helpKey, labelKey}` pairs asserting the help string contains the label's term per locale, was **built and rejected on evidence** (#688, 2026-09-05): deriving pairs mechanically from the `<strong>…</strong>` spans help prose uses to name controls yields 81 pairs, of which **12 fail in `es` and 20 in `tl` with no defect present**, because the assertion cannot survive ordinary grammar — Spanish number agreement (label `Vendibles`, prose *vendible*), the Tagalog plural marker (label `Mga Ibon`, prose *kasalukuyang ibon*), and above all Tagalog verb-focus affixation, where `nabebenta` / `naibibenta` / `maibebenta` are one word inflected three ways: the label form is not a substring of the other two, and the three share **no common prefix at all** — what they share is the root `benta` behind different prefixes, so `includes(label)` and stem-prefix matching both fail, and the only thing that would catch the pair is root extraction, which for Tagalog means either a stemmer or a hand-maintained root per term (the per-locale table this record declines below, arrived at from the other direction). That last case is disqualifying rather than merely inconvenient: `tl` is the locale #678's defect actually landed in, so a guard skipped for `tl` is a guard that does not exist. What replaces it is a **procedure**: when you add or change help/glossary prose that names a labelled control, look up what that control's label says **in each locale** and use that word — the label is authoritative, the prose follows it, and a locale must never disagree with itself about the same control. The same investigation, run once by hand, found two live instances in `tl` and both are fixed in the PR that recorded this decision: **four strings across two concepts** — `help:gradesBuckets`, `glossaryGradeDef` and `help:dailyLoopChain` all called the saleable thing *nabibili* (buyable) while `grades:saleableLabel` says **nabebenta** and `grades:intro` already said *nabebentang grado*, so the catalog disagreed with itself; and `farmSettingsIntro` listed the fourth farm setting as *unit system* while `settings:unitSystemLabel` says **Sistema ng yunit** — note the other three in that sentence (`Time zone`, `Locale`, `Currency`) are deliberate loanword labels and matched already, which is why only one of four was wrong. **Nothing enforces this; it relies on review** — that is the decision, not an oversight, and it is the one rule here whose enforcement line says so. Two things would reopen it: a locale pack whose morphology the assertion *can* survive (the check is viable for `en` alone, which is not worth a file), or a decision to maintain a per-locale term table naming the exact word each locale must use for each concept — priced and declined here because it is a third catalog, hand-maintained, and every new term needs an `es`/`tl` judgement the repo defers to native review under #182. Related: #662 (`badgeCase.test.ts`), the precedent that this repo *does* pin string content mechanically when the property is language-neutral — casing is, word choice is not.
