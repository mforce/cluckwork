# Migrations: `InitialCreate` frozen, one migration per change (#407)

> **Rule** — the one-paragraph version lives in [`AGENTS.md`](../../AGENTS.md); this file is the relocated rationale (what shipped, why the short version was insufficient, what not to break).

**Migrations: `InitialCreate`, then one per change — the #407 cutover.** `Persistence/Migrations/` began as exactly **one** migration, `InitialCreate`, generated from the current model on 2026-08-01. It replaced the 34 that had accumulated since 2026-06-27 (12 of them carrying raw SQL written for mid-history data states — backfills that touch 0 rows on an empty database but still execute). Done once, before the first production deploy, precisely because no `__EFMigrationsHistory` anywhere needed baselining.

**That squash is over, and so is the rule that came with it.** While the app had never been deployed, a schema change was *hand-folded into `InitialCreate`* — legitimate only because no database had applied that file yet. **PR #407 is the last change permitted to do that.** From the commit that merges it, **every schema change gets its own migration** (`dotnet ef migrations add <Name>`); `InitialCreate` is frozen. EF never re-runs an already-applied migration, so a hand-folded column is a column that **silently does not exist** on any database that already booted — and it fails as broken behaviour, not as a migration error. That is not hypothetical: it is exactly what #399's amendment did to the dev database, surfacing as a broken login. `MigrationSecurityReviewTests` enforces the new shape instead of the old `Assert.Single` fence, in **two** parts, and the second is the load-bearing one: (1) `InitialCreate` must stay **first** and keep its recorded id `20260801190854_InitialCreate`; (2) its **operations are frozen** by a pinned count + digest over a structural description of every `UpOperation`. Identity alone is not enough and that gap is the whole regression — editing `InitialCreate.cs` to add a column changes neither the class name nor the `MigrationAttribute`, and the other tests in that file only inspect credential-shaped inserts, the reference-data SQL, and the four expression indexes, so an ordinary `AddColumn`/`CreateTable` edit was invisible to all of them (#407 codex review). Note the count alone would not have caught it either: a column folded into an existing `CreateTable` leaves the operation count unchanged and moves only the digest. The digest walks **every public readable property** of each operation, recursing into nested column definitions, constraints, foreign keys and annotations, ordered by property **name** (never reflection order — `GetProperties()` is unspecified, same hazard as `GetTypes()`). It is emphatically **not** a hand-written list of "the properties that matter": that was the first attempt and it missed a column's `defaultValue` and a `CreateTable`'s nested keys, so changing `AspNetUsers.CredentialEpoch` from `defaultValue: 1` to `0` — a value #364 says is **permanently retired** — left the count and the whole digest unchanged (#407 codex review round 2). A property is now included because it *exists*, not because someone remembered it. Sequence order inside a collection is preserved rather than sorted, since a composite key's column order is itself schema. **Annotations are enumerated explicitly via `GetAnnotations()`**, because EF exposes them through a *method*, not a property — a property walk never reaches them, and the version that merely claimed to cover them let `Npgsql:ValueGenerationStrategy` flip from `IdentityByDefaultColumn` to `IdentityAlwaysColumn` with the test still green (#407 codex review round 3). Sorted by name there, since `IReadOnlyAnnotatable` promises no order. A `System.Type` is a **leaf** (described by `FullName` only): recursing into one reaches `Assembly.Location`, so the digest encoded an absolute path to `System.Private.CoreLib.dll` and differed between a dev box and the CI runner — green locally, red in CI, which is the worst shape for a fence because the tempting "fix" is to re-baseline until CI agrees, after which it guards nothing. `InitialCreate_Description_ContainsNoEnvironmentSpecificData` now asserts the described text names no assembly file and contains neither the runtime nor the test-binary directory. Successive rounds of this fence each shipped a comment asserting coverage the code did not have; **the standard for changing it is a mutation that goes red, not an argument that it should** — and for anything digest-shaped, **running it repeatedly on one machine proves nothing about portability**, which is exactly how the path leak reached CI.

**Never regenerate `InitialCreate`.** Two things in it are **hand-carried and un-regenerable** — a plain `dotnet ef migrations add` drops both on the floor: (1) the four **`lower("Name")` expression unique indexes** (`IX_EggGrades_AccountId_FarmId_LowerName`, `IX_ExpenseCategories_NameCi`, `UX_InventoryItems_Account_Farm_LowerName`, `IX_Products_AccountId_LowerName`) — EF cannot model a functional index, and losing them loses four uniqueness constraints; (2) the **static base reference data** raw SQL (see [`283-migrations-base-provisioning.md`](283-migrations-base-provisioning.md)). Regenerating also mints a **new timestamp**, which reorders it behind the migrations that depend on it and desynchronises `__EFMigrationsHistory` on every deployed database. `MigrationSecurityReviewTests` and `BaseReferenceDataMigrationTests` fail if any of that goes missing.

A database predating the squash (an old dev DB from `deploy/docker-compose.dev.yml`, an old demo/sim instance) still cannot migrate forward — **drop and recreate**: `docker compose -f deploy/docker-compose.dev.yml down -v && docker compose -f deploy/docker-compose.dev.yml up -d`. Same for any dev database created *before* #407 merged, since the columns it folded in will otherwise be absent.
