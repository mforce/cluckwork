# SPA E2E lives in `tools/simulation/ui/` (#277/#385)

> **Rule** — the one-paragraph version lives in [`AGENTS.md`](../../AGENTS.md); this file is the relocated rationale (what shipped, why the short version was insufficient, what not to break).

**SPA E2E lives in `tools/simulation/ui/` (#277/#385), not in `web/`.** Playwright drives the real built SPA against the **same** `seed --profile simulation` fixture k6 uses, so screens are populated rather than empty; `web/` stays Vitest + Testing Library. Three rules it exists to enforce, all of which have already caught something: **never hardcode a credential** (personas come from the git-ignored `.sim-cast.json`, same file k6 reads), **never hardcode English** (selectors resolve through the SPA's own en/es/tl catalogs — a missing key throws rather than falling back, so an es spec cannot assert an English string and pass), and **respect the farm clock** (`America/Chicago` is behind UTC, so a UTC "today" is refused both by the report endpoints and by every date input's `max`). The suite is **mutation-checked** — `npm run mutation` breaks a guarantee at the network boundary and requires the covering spec to go red; a red baseline aborts the run, because a mutation pass over an already-failing suite reads exactly like success. **The quick suite runs on pull requests** (`.github/workflows/e2e-smoke.yml`; owner call 2026-08-08, revising the original dispatch-only decision after #433 merged a session-contract change that silently broke the suite — the exact #370 rot the old header warned about, and the old "6-10 billed minutes" estimate had gone stale at a measured ~3). It is path-filtered to what the suite can observe and cancels superseded runs. The `slow` (real 15-minute expiry) and `canary` modes remain `workflow_dispatch`-only, as does the k6 sibling — the #370 warning still fully applies to those, and a PR run exercises the *second* browser path (downloaded Chromium; the NixOS dev box uses a system one, because the downloaded binaries do not launch there).

## Accessibility assertions must go through CDP (#501)

**Playwright's own accessibility surface does not model `inert`.** Probed against a standalone page, not assumed: with a wrapper flipped to `inert`, `locator.ariaSnapshot()` still lists its children, and `isVisible()`/`isEnabled()` still return `true`; only `click()` notices, and only by timing out. CDP `Accessibility.getFullAXTree` is the one that agrees with the spec — the node is absent from the tree entirely. So a spec asking "is this out of the accessibility tree while a dialog is open?" through `getByRole` or `ariaSnapshot` **passes whether or not the app inerts anything**, the same shape of tautology as asserting the service-worker navigation denylist with `fetch()` instead of a navigation. `src/ax.ts` is the only sanctioned reader; it reports `inDom` separately from `inTree`, because absence is also what a mistyped selector looks like, and every absence assertion is paired with a control node that must still be present in the same snapshot.

Two consequences worth keeping in view. First, `ax.node()` is a single CDP round trip with **no auto-retry**, unlike a locator, so every read must follow a settled Playwright signal — the first run of `a11y-live-regions.spec.ts` reported the announcer as unmounted purely because React had not painted. Second, the mutation harness gained its **first DOM-level mutants** here (`a11y-*`), because a live region's place in the accessibility tree is not something a server response can decide; `src/mutants.ts` records what that instrument is and is not faithful to, and warns that a DOM mutant which fails to install is indistinguishable from a surviving one.

**None of this observes an announcement.** Presence in the tree is the precondition; whether an assistive technology speaks is a manual pass — [`docs/runbooks/screen-reader-verification.md`](../runbooks/screen-reader-verification.md).

## The suite runs at two widths (#814)

**Until #814 the suite had rendered the app at exactly one size.** `playwright.config.ts` declared a single project spreading `devices["Desktop Chrome"]`, which carries a 1280x720 viewport, so every spec on every pull request since 2026-08-08 had only ever seen a desktop window — while the product's primary context is a phone in a hen house, which is the stated reason #674 chose direction B. #740 is the proof that gap let something through: a control that reads as one 40px line at 1280 renders 100px wide by 103px tall at 420, where `border-radius: 999px` clamps into an ellipse and the label sits outside its own background. English was the worst of the three locales there, so a translated run would not have caught it either.

**Two projects partitioned by the `@phone` tag, differing in the viewport and nothing else.** `chromium` runs at 1280 with `grepInvert: /@phone/`, `chromium-phone` at 390x844 with `grep: /@phone/`; every test runs in exactly one. The frame is set **after** the `devices[...]` spread, the same trap `playwright.screenshots.config.ts` documents — above it the phone specs silently run at 1280. Holding everything else equal is deliberate: a spec red in one project and green in the other is then attributable to width alone, which is the whole evidentiary value of the split. `devices["Pixel 7"]`, `isMobile` and `hasTouch` were **measured and rejected** — both emulation modes reported identical `scrollWidth`/`clientWidth`/`innerWidth` on all six walked routes and an identical tab-bar rect, so they buy nothing here while adding touch dispatch and a mobile UA. The cost is named rather than implied: `isMobile` drives Chromium's mobile layout-viewport sizing, so a #441-class regression on a real device is **not** covered.

**The `nav` fixture throws under the phone layout, and that refusal is the load-bearing part.** Below 900px the sidebar is `display: none` and BottomNav owns navigation, showing four tabs with everything else inside a *closed* dialog. So `expect(nav.link(k)).toBeHidden()` — how `worker`, `readonly` and `session-races` each prove a role gate — would mean "the sheet happens to be shut" rather than "this role may not go there", and pass while the gate stood open. Making the fixture unavailable turns that from something a reviewer must notice into a construction error. For the same reason a `MoreSheet` is obtainable **only** from `openMore()`, so a sheet-link locator always refers to an open sheet. `signIn` correspondingly moved off the `complementary` landmark to `main#main-content`, structural rather than labelled (an es/tl persona must still be able to sign in) and present at both widths; it is honestly narrower, proving the shell mounted and no longer that any nav chrome rendered.

**A third mutation boundary, and the instrument is not the obvious one.** Layout is neither a server response nor a DOM node, and **an injected `<style>` element is silently blocked**: the app ships `Content-Security-Policy: style-src 'self'` with no `'unsafe-inline'` and no nonce, so a script-created `<style>` parses to nothing — measured, `sheet === null` while the element sat in `<head>`. `page.addStyleTag` builds exactly that element. This is the #501 warning wearing a different hat: a CSS mutant that never installed reports as a *surviving* one, accusing the spec of being vacuous when the mutant is what failed to run. `page.route` on the stylesheet does not work either, because a service worker serves the original from cache on every load after the first. What works is `insertRule` on the sheet the page already loaded — CSP governs loading a style resource, not later edits to an already-allowed same-origin one.

**`PROJECT_FOR` is required in `mutation-check.sh`, and `MUST_STAY_GREEN_ON` asks the question a kill cannot.** A defaulted project would run a phone mutant at 1280, where its spec does not exist, and report a survivor — an accusation against a spec that never executed; `EXPECT_MSG_FOR` and `FALSE_KILLS` each started advisory in that file and each let the score overstate itself until a review round made them mandatory. Killing a phone spec at 390 proves the spec noticed *something*, not that the something was width-specific, so each phone mutant additionally re-runs the whole desktop suite and must leave it green. All three do.

**The walk asserts, it does not discover.** Its route list is every screen whose main content is a `table.data` — the thing #441's containment holds in — plus `/`, which carries no table but does carry the widest intrinsic content in the app, a money string in a `max-content` grid track. Each route names the content being judged, because a shared `table.data` selector was tried and `/daily-entry` has no table at all; and naming it is also what stops a route rendering an error page, measuring exactly 390 and reporting clean.

**A measurement is only as current as the bytes that produced it.** `/` was excluded from that walk for most of this PR's life, on a probe showing the dashboard at 443/390 with a 13-character amount pushed off screen. That reading was real and it was **stale**: the sim stack had been up 28 hours, serving an image built before #781 (`7193ebe`, 2026-09-12), the commit that gave that list its container-query narrow layout — and which is seven commits behind this branch's own base. Rebuilt, the same rows measure 390/390, the list resolves to `grid-template-columns: 179.219px 112px`, and the widest amount sits at x=346.6 inside a 353px panel. An issue was filed against the phantom and withdrawn. The rule that would have prevented it is already written down two sections above in AGENTS.md — a long-running sim stack serves the bytes it was built from, not the branch under review — so the lesson is not a new rule but the cost of skipping an old one: **rebuild before believing a rendered measurement**, including a measurement that is only being used to justify an exclusion.
